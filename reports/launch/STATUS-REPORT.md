### چرا این کار نشده؟ (پاسخ صادقانه)

سه دلیل مشخص:
1. **اولویتبندی فازها:** تا الان تمرکز روی A-Gates بوده (امنیت P0، پرداخت، موتور نجومی، گزارش AI، سئو، CI، مانیتورینگ) — همهٔ اینها پیشنیاز لانچاند. مدیریت محتوا «عملیات پس از لانچ» است، نه «پیشنیاز لانچ».
2. **محتوای فعلی از قبل تولید شده:** ۵۰ مقالهٔ سئو + ۳۰ مقالهٔ اولیه + صفحات راهنما/درباره/FAQ توسط من با cron ساخته و لود شدهاند — تا قبل از لانچ، «کسی غیر از ما محتوا نمیسازد» فرض درستی بود.
3. **عملکرد:** خودت برنامهنویس نیستی و محتوا را من تولید میکنم — برای همین CMS بهعنوان «کار راحتتر من» عقب افتاد. **اما حق با توست:** بعد از لانچ، تو باید بتوانی مقاله بنویسی/ویرایش کنی، متن تخفیف بنری را عوض کنی، صفحهٔ جدید بسازی — بدون اینکه منتظر من باشی. این واقعاً جزو موارد اصلی عملیات است.

### پیشنهاد: CMS ادمین (اگر تأیید کنی بعد از لانچ یا همین حالا میسازم)

- تب «محتوا» در پنل: لیست مقالات + ساخت/ویرایش/حذف
- فیلدها: عنوان، اسلاگ، دسته، خلاصه، توضیح متا، تصویر، بدنه (بخشهای h2/p)، تاریخ شمسی
- ویرایش متن صفحات کلیدی (خانه/راهنما/درباره/FAQ/قوانین) از پنل با کلیدهای متن
- ذخیرهٔ اتمیک + بکاپ خودکار قبل از هر نوشتن + لاگ ممیزی (تغییرات از همین پنل ردیابی میشود)
- ذخیره در DB (نه JSON) با migration — مقالات قبلی seed میشوند
- تست + CI + deploy — بدون هزینهٔ اضافی

## ۲) سازوکار آپدیت سایت بعد از لانچ (سوال مهم تو)

### زیرساخت فعلی (همه واقعی و زنده):

```
GitHub (private: Mahdiyar-eth/chart-platform)
   │  git push
   ▼
GitHub Actions CI  →  Postgres 16 + Redis تست  →  scripts/ci.sh
   │   (ruff + 522 تست + bandit + pip-audit + secret-scan + brand-scan
   │    + alembic check = schema drift)
   ▼
سرور Hetzner (chart.negar.io)
   │  bash scripts/deploy.sh --migrate
   │    = git pull --ff-only → alembic upgrade head → alembic check
   │      → restart chart-web + chart-worker → homepage 200
   ▼
عمران روزانه: بکاپ DB+config 03:15 → R2 · واتچداگ ۵ دقیقهای · دریل بازیابی هفتگی
```

### جریان کار من برای هر فیچر جدید یا فیکس بعد از لانچ:

1. **من کد را روی سرور تغییر میدهم، تست مینویسم، رگرسیون کامل میزنم** (فرقی با الان ندارد — همان محیط)
2. commit + push به GitHub → **CI خودکار اجرا میشود** (اگر چیزی شکست، همانجا معلوم میشود)
3. `bash scripts/deploy.sh --migrate` → انتشار بدون قطعی معنی (restart ~۲ ثانیه)
4. smoke خودکار (homepage 200 + health) + در صورت نیاز تست دستی من
5. هر تغییری که **schema دیتابیس** را عوض کند → **alembic migration** → امن است چون `alembic check` قبل و بعد از migrate جلوی drift را میگیرد
6. **قبل از هر deploy بکاپ وجود دارد** (روزانه 03:15 + دریل restore هفتگی که واقعاً تست میشود — آخرین بار: ۲۹ کاربر، ۸ سفارش restore شد)
7. اگر deploy خراب شود → **rollback: git checkout <commit قبلی> + deploy** — چون git تاریخچهٔ کامل دارد (از الان tag های نسخه داریم)

### چه چیزهایی بعد از لانچ فرق میکند؟

- **دادهٔ واقعی:** هر deploy با migrate باید محافظهکارانهتر باشد — دقیقاً همین الان هم هست (migration + check + backup قبل)
- **کوتاه کردن خطا:** واتچداگ ۵ دقیقهای (خطای 500 → تلگرام), uptime-watchdog, disk-watchdog — همه از قبل فعالاند
- **هیچ deploy خودکار بدون CI سبز** — قانون
- **هزینهٔ AI زنده است:** سقف روزانهٔ LLM (۳ دلار) — اگر تمام شود، گزارشها degraded صادقانه میشوند (نه قبض عجیب)

**نتیجه:** بعد از لانچ، تو هیچ کاری برای آپدیت انجام نمیدهی — من فیچر را مینویسم، تست میکنم، deploy میکنم و به تو گزارش میدهم. اگر بخواهی «صفحهای را خودت تغییر دهی»، همان CMS (بخش ۱) که پیشنهاد دادم لازم است.
