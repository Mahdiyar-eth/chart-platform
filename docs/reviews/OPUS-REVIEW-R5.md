### 🔴 P0-1 — گیت drift **شکسته است**: drift را می‌بیند، `FAILED` چاپ می‌کند، ولی `exit 0` می‌دهد

**این پاسخ مستقیم به سؤال تمرکز ۲ شماست: «آیا ad-hoc migration بدون مهاجرت Alembic از حالا گیر می‌افتد؟» → ❌ نه.**

**بازتولید (اجرا شد):** یک جدول به `app/models.py` اضافه کردم **بدون** مهاجرت:
```
$ bash scripts/drift_gate.sh > /tmp/drift_neg.log 2>&1
$ echo "REAL_EXIT_CODE=$?"
REAL_EXIT_CODE=0                    ← ❌ موفق!

$ tail -4 /tmp/drift_neg.log
ERROR [alembic.util.messaging] New upgrade operations detected: [('add_table', Table('_drift_probe_tbl' ...
FAILED: New upgrade operations detected: [('add_table', Table('_drift_probe_tbl' ...
drift db dropped
==> drift gate OK                   ← ❌ می‌گوید OK
```
گیت drift را **درست تشخیص داد** ولی اسکریپت با کد ۰ خارج شد و «drift gate OK» چاپ کرد.
`scripts/ci.sh` هم آن را با `bash scripts/drift_gate.sh` صدا می‌زند ⇒ **CI سبز می‌ماند**.

**علت ریشه‌ای — اثبات‌شده با مقایسهٔ نسخه‌ها:**
```
fbf283e:scripts/ci.sh:28       DATABASE_URL="$DRIFT_DB" venv/bin/alembic check
scripts/drift_gate.sh:36       DATABASE_URL="$DRIFT_DB" venv/bin/alembic check && echo "DRIFT-GATE: CLEAN"
```
نسخهٔ قدیم دستور را **تنها** اجرا می‌کرد ⇒ `set -e` روی شکستش فعال می‌شد.
نسخهٔ جدید آن را در یک لیست `&&` گذاشته؛ طبق قواعد bash، فرمانی که **سمت چپ `&&`** است
از `set -e` **معاف** است. پس شکست بلعیده می‌شود.

⇒ **ریفکتور `W5` (استخراج `drift_gate.sh`) این رگرسیون را ساخت** — و دقیقاً همان گیتی را
از کار انداخت که `Z4` برای جلوگیری از تکرار حادثهٔ «جدول `subscribers` بدون مهاجرت» نوشته بود.

> نکتهٔ مهم: **گیت روی کد فعلی درست پاس می‌شود** (تست مثبت را هم زدم: `DRIFT-GATE: CLEAN`
> روی DB واقعاً خالی، و `subscribers` حالا مهاجرت دارد ✅). مشکل فقط این است که
> از این پس هر drift جدیدی **بی‌صدا** رد می‌شود.

**فیکس یک‌خطی:** `&& echo` را بردار، یا `if ! alembic check; then exit 1; fi` بنویس.

### 🟠 P1-1 — fallback محلی R2 **فقط نوشتن** است؛ فایل هرگز قابل بازیابی نیست

**تمرکز ۳ شما — بخش اول: آیا fail-closed تولید ضعیف شد؟ ❌ نه، سالم است.**

`app/storage.py`:
```python
if IS_PROD and not (R2_ACCESS and R2_SECRET and R2_ENDPOINT):
    raise RuntimeError("R2 storage is REQUIRED in production ...")   # سطح ماژول

def configured() -> bool:
    return bool(R2_ACCESS and R2_SECRET and R2_ENDPOINT)             # دقیقاً همان سه متغیر
```
گارد و شرط fallback **از یک مجموعه متغیر** استفاده می‌کنند ⇒ در تولید اگر ماژول اصلاً
import شده باشد، `configured()` الزاماً True است ⇒ **شاخهٔ fallback در تولید غیرقابل‌دسترس است.** ✅
تست‌های امتناع در `ci.sh` (بندهای ۱، ۱b، ۱c) هم **دست‌نخورده‌اند** و بند ۱b صراحتاً
`R2_ACCESS_KEY_ID= R2_SECRET_ACCESS_KEY= R2_ENDPOINT=` را خالی می‌کند تا env محیط را override کند ✅
(کلیدهای dummy فقط به بند ۲ — تست بوت **موفق** — داده شده‌اند که جای درستی است.)

**اما یک ایراد واقعی:** `presigned_url()` هیچ fallback محلی ندارد:
```python
def presigned_url(key, expires=1800):
    if not configured() or not key:
        return None
```
و `grep -rn "MEDIA_DIR\|_local_media_path" app/ | grep -v storage.py` ⇒ **خالی** —
هیچ روتی `/tmp/chart-media` را سرو نمی‌کند.

⇒ در dev/CI، `upload_bytes` فایل را روی دیسک می‌نویسد و `True` برمی‌گرداند، ولی فایل
**هرگز قابل خواندن نیست**. تست «رسانهٔ CMS» فقط موفقیت نوشتن بایت را assert می‌کند، نه کارکرد قابلیت را.
یعنی تست «legitimately» پاس می‌شود اما سطحی‌تر از آنچه به نظر می‌رسد.

## قانون دور بعد

**قانون «گیت را با شکست تست کن، نه با موفقیت».**
سه دور است گیت‌ها را با «سبز شدنشان» تأیید می‌کنیم. اما یک گیت که همیشه سبز است،
از یک گیت شکسته قابل تشخیص نیست. `P0-1` دقیقاً همین بود: گیت drift روی کد سالم `CLEAN`
می‌داد و همه خیال می‌کردند کار می‌کند — تا وقتی که عمداً خرابش کردم.

**برای هر گیت (drift، abs-path، brand-language، secret-scan، fail-closed):**
یک تست منفی بنویس که ثابت کند گیت **وقتی باید، قرمز می‌شود**.
