## 🔴 یافتهٔ جدید — بازگشت اعتبار در تحلیل گذر **کمتر از حق کاربر** است

**شدت:** P1 مالی — دقیقاً وقتی فعال می‌شود که LLM خراب باشد، یعنی بدترین لحظه.

**کشف با اجرای زنده.** دفتر اعتبار واقعی از قیف من:
```
 amount |               reason               
--------+------------------------------------
     25 | topup
     -7 | report_full
     -2 | transit_3m
      2 | transit_3m partial QA refund (5/8)     ← ۵ از ۸ شکست، ولی کل مبلغ برگشت
```
اینجا بی‌ضرر بود (اتفاقی)، ولی ریاضی‌اش غلط است:

**علت ریشه‌ای — مخرج اشتباه:**
- `app/report/transit_narrative.py:143` — `top = sorted(events, key=-weight)[:n]`
  فقط **n رویداد** روایت می‌شود (۳ماهه → ۵ · ۱۲ماهه → ۱۲)
- `app/main.py:2516` — `total_ev = len(events) or 1` ← **همهٔ** رویدادها، نه n
- `app/main.py:2521` — `if failed_n >= total_ev:` بازگشت کامل
  ⇒ چون همیشه `failed_n ≤ n < total_ev`، **این شرط هرگز درست نمی‌شود**
- `app/main.py:2524` — `ceil(price × failed_n / total_ev)`

**سناریوی شکست قطعی (محصول ۵ اعتباری ۱۲ماهه):**
```
چارتی با ۳۰ رویداد · ۱۲ رویداد روایت می‌شود · هر ۱۲ گیت QA را رد می‌کنند
⇒ کاربر صفر روایت می‌گیرد
failed_n=12 · total_ev=30 → 12 >= 30 نادرست → شاخهٔ جزئی
بازگشت = ceil(5 × 12/30) = 2 اعتبار
⇒ کاربر ۵ اعتبار داد، هیچ نگرفت، فقط ۲ برگشت — ضرر خالص ۳ اعتبار (~۱۵۰٬۰۰۰ تومان)
```
در اجرای من فقط به‌خاطر گرد کردن (`ceil(2×5/8)=2`) کل مبلغ برگشت — شانس بود، نه طراحی.

**فیکس:** مخرج باید **تعداد روایت‌شده** باشد نه کل رویدادها.
`narrate_transit` همین حالا `metrics["events"] = len(top)` را برمی‌گرداند (خط ۱۴۶) —
از همان استفاده شود.
