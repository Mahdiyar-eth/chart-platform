## بخش ۰ — داوری کلی

**کاری که خوب انجام شده (واقعاً خوب):**
- `app/credits.py` — سرویس اعتبار تمیز، خرج اتمیک با `RETURNING`، idempotency، کد خطای پایدار. قانون «هیچ `SET credits` بیرون از این فایل» **واقعاً برقرار است** (گرپ زدم: خالی).
- `app/static/css/tokens.css` — توکن‌های واقعی و باکیفیت (رنگ، مقیاس ۸ نقطه‌ای، z-index، تم روشن). این بهترین فایل این دور است.
- `app/astrology/transit_forecast.py` — موتور گذر با bisection و گیت مجاورت برای رفع sign-flip کاذب `norm180`. کار مهندسی درست.
- `app/nav.py` — رجیستری واحد ناوبری، دقیقاً همان چیزی که پلن خواست.
- `docs/qa/ui-audit-2026-08-22/` — ۹۵ اسکرین‌شات از ۱۹ صفحه × ۵ سایز. کار واقعی انجام شده.
- هدرهای امنیتی، CMS، پنل ادمین اعتبار، مهاجرت‌ها — همه موجود و منسجم.

**مشکل اصلی — یک الگوی تکرارشونده:**

> **زیرساخت ساخته شد، اما به محصول وصل نشد.**

سه نمونهٔ قطعی:
1. `POST /api/purchase` (قلب اقتصاد اعتبار) **از هیچ صفحه‌ای صدا زده نمی‌شود** — در هیچ قالب و هیچ JS نیست.
2. `partials/credit_cta.html` ساخته شد اما **در هیچ قالبی `include` نشده**.
3. `entitlements.consume()` نوشته و تست شد اما **هیچ‌جای برنامه صدا زده نمی‌شود**.

نتیجه: از بیرون، کاربر تقریباً هیچ‌کدام از این قابلیت‌ها را نمی‌بیند. تست‌ها سبزند چون
**API را تست می‌کنند، نه مسیر کاربر را**. این دقیقاً همان تلهٔ «کد وجود دارد ≠ feature کار می‌کند»
که در `docs/PLAN-V7-MASTER.md` بخش ۰ سال‌ها پیش هشدار داده شده بود.

## بخش ۱ — یافته‌های بحرانی (🔴 P0 — قبل از هر کار جدید)

### R1 — صفحهٔ گذرهای پیش‌رو **بلافاصله بعد از پرداخت خراب می‌شود**
**شدت:** 🔴 بحرانی — پرچم‌دار محصول جدید، دقیقاً در لحظهٔ بعد از پرداخت.

**زنجیرهٔ خطا:**
1. `transit_cache.store_transit_analysis()` (خط ۵۲-۶۸) شکل رکورد کش را از **لیست** به **دیکشنری** `{"events":[...], "narratives":[...]}` تبدیل می‌کند.
2. `cached_forecast()` (خط ۳۴) بدون هیچ نرمال‌سازی `json.loads(row.payload_json)` را برمی‌گرداند → بعد از خرید، **دیکشنری** برمی‌گردد.
3. `transits_page()` (`main.py`) خروجی را مستقیم به قالب می‌دهد: `"events": ev12`.
4. `transits_forecast.html:77` می‌نویسد `events: {{ events|tojson }}` → در جاوااسکریپت یک **آبجکت** می‌شود.
5. `x-if="events.length"` روی آبجکت `undefined` است → falsy.
6. **کاربر این را می‌بیند:** `رویداد گذری در این بازه محاسبه نشد.`

یعنی کاربر ۵ اعتبار می‌دهد و صفحه به او می‌گوید هیچ گذری وجود ندارد.

**چرا تست نگرفتش:** `test_transits_page_renders` فقط حالت **قبل از خرید** را تست می‌کند و
`test_analyze_success_spends_credit` فقط API را. هیچ تستی «خرید → بارگذاری دوبارهٔ صفحه» را پوشش نمی‌دهد.

**فیکس:** در `cached_forecast` خروجی را همیشه نرمال کن:
```python
data = json.loads(row.payload_json)
return data.get("events", []) if isinstance(data, dict) else data
```
**تست اجباری:** analyze کن → `GET /transits/{id}` → assert رویدادها در HTML هستند و پیام «محاسبه نشد» نیست.

### R2 — تحلیل گذر: **تولید نامحدود رایگان با LLM پولی**
**شدت:** 🔴 بحرانی — سوراخ هزینه، قابل سوءاستفاده.

`main.py` (اندپوینت analyze):
```python
tx = spend(session, user.id, action, idempotency_key=f"transit:{chart_id}:{months}", ...)
```
کلید idempotency **دائمی** است و به هیچ رویداد یکتایی گره نخورده. پس:
- بار اول: ۵ اعتبار کم می‌شود.
- **بار دوم به بعد: `spend` همان تراکنش قبلی را برمی‌گرداند (صفر اعتبار)** و کد بدون هیچ چک کشی به `narrate_transit` می‌رود → ۱۲ فراخوانی LLM پولی، رایگان، **بی‌نهایت بار**.

یک کاربر با یک خرید ۵ اعتباری می‌تواند بی‌نهایت تولید LLM بگیرد.

**فیکس:**
1. کلید را به کاربر و دوره گره بزن: `f"transit:{user.id}:{chart_id}:{months}:{YYYY-MM}"`
2. **قبل از** تولید، کش را چک کن: اگر `narratives` موجود است، همان را برگردان و LLM را صدا نزن.

### R4 — **تولید گزارش اصلاً به اقتصاد اعتبار وصل نشده**
**شدت:** 🔴 بحرانی — گران‌ترین محصول (۷ و ۱۴ اعتبار) با اعتبار قابل دریافت نیست.

`api_create_report` هنوز فقط این را می‌پذیرد:

### R5 — استحقاق گزارش **بدون `ref_id`** ساخته می‌شود ⇒ همهٔ گزارش‌ها باز می‌شوند
**شدت:** 🔴 بالا — منطق per-report که در داکسترینگ وعده داده شده، برقرار نیست.

- `_report_gate` می‌گوید: `ent_has(session, uid, "report", ref_id=rep.id)`
- ولی `api_purchase` هرگز `ref_id` پاس نمی‌دهد → استحقاق با `ref_id=None` ساخته می‌شود.
- در `entitlements.has()`:
  ```python
  if ref_id is not None and ent.ref_id and ent.ref_id != ref_id: continue
  ```
  چون `ent.ref_id` تهی است، شرط رد می‌شود ⇒ **آن استحقاق با هر گزارشی مطابقت می‌کند.**

بدتر: `payload.chart_id` اختیاری است. اگر `null` بفرستی، `ent.chart_id=None` هم می‌شود ⇒
**یک خرید ۳ اعتباری `report_basic` = دسترسی به همهٔ گزارش‌های همهٔ چارت‌های آن کاربر، برای همیشه.**
(`quantity=1, used=0` هرگز مصرف نمی‌شود چون `consume` صدا زده نمی‌شود.)

**فیکس:** `chart_id` را برای اکشن‌های چارت‌محور **اجباری** کن؛ در `has()` منطق را برعکس کن —
وقتی `chart_id`/`ref_id` درخواست شده، استحقاقِ **بدون** اسکوپ نباید قبول شود (مگر با پرچم صریح `global=True`).

### R6 — `grant_from_credits` اتمیک نیست: اعتبار می‌رود، استحقاق ساخته نمی‌شود
**شدت:** 🔴 بالا — پلن صراحتاً «هر دو در یک تراکنش DB» را خواسته بود.

```python
tx = spend(...)          # ← این خودش commit می‌کند
ent = Entitlement(...)
session.add(ent); session.commit()   # ← تراکنش دوم
```
کرش/خطا بین دو commit ⇒ اعتبار کم شده، استحقاقی وجود ندارد.
(به‌خاطر idempotency، **تلاش دوباره با همان کلید** ترمیمش می‌کند — ولی این شانس است نه طراحی.)

**فیکس:** `spend(..., commit=False)` اضافه کن (مثل `grant`) و هر دو را در یک commit ببند.

### R7 — بستهٔ چت: **هرگز مصرف نمی‌شود، هرگز منقضی نمی‌شود**
**شدت:** 🔴 بالا — ۲ اعتبار = چت نامحدود مادام‌العمر.

- `entitlements.consume()` نوشته شده ولی **در کل برنامه صدا زده نمی‌شود** (گرپ زدم: صفر فراخوانی).
  `POST /api/chat` استحقاق را مصرف نمی‌کند ⇒ `used` همیشه ۰ ⇒ `_usable` همیشه True.
- `grant_from_credits` هیچ‌وقت `expires_at` ست نمی‌کند ⇒ عنوان محصول («اعتبار ۳۰ روزه») یک **وعدهٔ شکستهٔ جدید** است.

**فیکس:** در مسیر ارسال پیام `consume()` را صدا بزن (و commit کن — `consume` خودش commit نمی‌کند)،
و `expires_at` را از یک نگاشت `action → مدت` ست کن.

### R13 — دیزاین‌سیستم: متریک پاس شد، هدف نه
- `style="` از ۹۶۵ به **۲۰** رسید ✅ … ولی با تبدیل به **۱۰۱۷ کلاس هش‌شده** مثل `.st-302eccda`.
- `generated.css` شامل **۱۵۶ رنگ هاردکد** و ۱۲۰ قاعده با `color:#...` بدون توکن است.
- پلن صریحاً گفته بود: «همهٔ رنگ‌ها فقط از توکن» و «مقیاس ۸ نقطه‌ای، هیچ عدد فاصلهٔ دلخواهی مجاز نیست».
- **پیامد واقعی و قابل مشاهده:** حالت روشن (C4) برای این عناصر **شکسته است**. مثال قطعی:
  `.st-6aa99fbc{color:#8fb6ff}` و `.st-74e1d4ce{color:#b8c2f0}` در `plans.html` استفاده می‌شوند —
  آبی روشن روی پس‌زمینهٔ سفید تم روشن ⇒ کنتراست فاجعه.
  توکن‌ها در تم روشن عوض می‌شوند، این رنگ‌ها نه.

این کلاسیک Goodhart است: عدد هدف زده شد، هدف واقعی (امکان تغییر سراسری) نه.
**فیکس تدریجی:** اسکریپت نگاشت هش→توکن؛ اولویت با رنگ‌های متن. برای پذیرش:
`grep -c 'color:#' app/static/css/generated.css` باید به صفر برسد.
و ممیزی کنتراست باید **در تم روشن هم** اجرا شود (الان فقط تاریک تست شده).

## بخش ۵ — سه قانون جدید برای هرمس (از درس‌های این دور)

1. **قانون «قابل دسترس بودن»:** یک اندپوینت یا کامپوننت تا وقتی از رابط کاربری قابل رسیدن نباشد،
   `DONE` نیست — حداکثر `PARTIAL`. قبل از بستن هر تسک این را اجرا کن:
   `grep -rn "<endpoint>" app/templates/ app/static/` — اگر خالی بود، تسک تمام نشده.

2. **قانون «تست از کلیک کاربر»:** برای هر قابلیت پولی حداقل یک تست باید از **صفحه** شروع شود، نه از API.
   هر سه باگ بحرانی این دور (R1، R2، R4) با یک تست سرتاسری واقعی گرفته می‌شدند.

3. **قانون «متریک ≠ هدف»:** اگر برای رسیدن به عدد هدف روشی انتخاب کردی که روحِ هدف را برآورده نمی‌کند
   (مثل R13)، **در گزارش صریح بنویس** «متریک زده شد ولی هدف کامل نشد، چون…». این را جریمه نمی‌کنم — پنهان‌کردنش را چرا.

## بخش ۶ — آنچه باید تصحیح شود در گزارش‌دهی

گزارش‌های هرمس **دقیق و صادقانه‌اند** جز در یک نقطه: بخش‌هایی که انجام نشدند به‌جای `PARTIAL`
با سکوت رد شده‌اند (E2 صفحات؛ اتصال UI اقتصاد اعتبار). فرمت بخش ۱۳ پلن اصلی این ستون را دارد — استفاده شود.

همچنین بخش ۵ فرمت («چیزهایی که پلن اشتباه پیش‌بینی کرده بود») در بیشتر گزارش‌ها خالی مانده،
در حالی که چند مورد واقعی وجود داشت (مثلاً پلن نگفته بود تولید گزارش هم باید به اعتبار وصل شود —
این **نقص پلن من** بود، نه هرمس؛ در پلن فقط گیت `_report_gate` نام برده شده بود).
