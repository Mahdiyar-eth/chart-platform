## ۲. 🔴 P0 — دو باگ پولی

### P0-1 · کد تخفیف LANCH20 حالا **پک اعتبار** را تخفیف می‌دهد (دقیقاً برعکس هدفش)

`LANCH20` یک کوپن `report_only=True` است — فقط برای **اولین گزارش عمیق**. اجرای واقعی:

```
create_order(credit12 + LANCH20) -> ACCEPTED | ۴۸۰٬۰۰۰ تومان   (قیمت کامل ۶۰۰٬۰۰۰)
create_order(credit3  + LANCH20) -> ACCEPTED | ۱۴۴٬۰۰۰ تومان   (قیمت کامل ۱۸۰٬۰۰۰)
```

علتش این خط جدید در `orders.py` است:
```python
if plan_key not in CREDIT_PACKS and plan_key not in DEEP_REPORT_ACTIONS:
    raise ValueError("این کد تخفیف فقط برای گزارش عمیق است")
```
قبلاً `if plan_key not in REPORT_PLANS: raise` بود و `credit3` رد می‌شد.
حالا پک‌ها **صریحاً مجازند**. و چون `REPORT_PLANS = set()` شده و اکشن‌های گزارش هرگز
به `create_order` نمی‌رسند، **تنها چیزی که LANCH20 می‌تواند تخفیف بدهد پک اعتبار است.**

گیت «اولین گزارش» هم روی ledger نگاه می‌کند؛ کاربر تازه هیچ ردیفی ندارد ⇒ کوپن معتبر
⇒ **هر کاربر جدید ۲۰٪ تخفیف روی پک اعتبار**، تا سقف `max_uses`.

> ⚠️ تستی که دقیقاً همین را می‌گرفت، **در همان کامیت حذف شد**:
> ```python
> with pytest.raises(ValueError) as e2:
>     create_order(s, "credit3", None, coupon="LANCH20", new_user_id=buyer)
> assert "گزارش عمیق" in str(e2.value)      ← حذف شد
> ```
> جایگزینش فقط `status_code` اندپوینت `/api/coupons/check` را می‌سنجد، نه رفتار پولی را.
> این مصداق خط قرمز ۲ است: تست موجود ضعیف شد و باگ از همان شکاف رد شد.

### P0-2 · «escrow» پک مهمان فقط یک **یادداشت** است، نه سازوکار

اجرای واقعی روی یک سفارش پک مهمان (بدون `user_id`):
```
grant_credits raises -> order ... has no resolvable buyer
order.status = 'paid'
ledger rows for this order: 0          ← هیچ اعتباری به هیچ‌کس داده نشد
مبلغ پرداختی: ۳۳۰٬۰۰۰ تومان
```
و `grep -rn "escrow" app/` فقط دو چیز پیدا می‌کند: همان کامنت و رشتهٔ `order.note`.
`claim_anonymous_charts` فقط `profile.user_id` را ست می‌کند — **هیچ‌جا کدی نیست که این
اعتبارها را بعداً اعطا کند** (نه هنگام ورود، نه هنگام claim چارت، نه در هیچ sweeper).

**این یک پس‌رفت است:** قبلاً استثنا بالا می‌رفت، کل verify رول‌بک می‌شد و سفارش
`pending` می‌ماند — یعنی پول آشکارا تسویه‌نشده و قابل‌پیگیری بود. حالا سفارش
**`paid`** علامت می‌خورد، پس هر گزارش مالی/استردادی آن را «فروش کامل‌شده» می‌بیند.

### P1-3 · روایتِ «باگ مالی» درست نیست — ولی خودِ فیکس ارزش دارد
با کد **قبل از R13** و ۴ نخ همزمان روی همان سفارش:
```
thread 0 -> CLAIMED+verified (blocked 0.00s)
thread 1 -> lost -> redirect (blocked 2.01s)
thread 2 -> lost -> redirect (blocked 2.01s)
thread 3 -> lost -> redirect (blocked 2.00s)
  gateway verify() would run 1 time(s)
```
قفل سطری PostgreSQL از قبل مانع دوباره‌verify شدن می‌شد؛ ادعای «۴ بار verify» و
«N بار پول» **نادرست** است. آنچه واقعاً خراب بود: هر بازنده یک کانکشن دیتابیس را
به‌اندازهٔ کل تأخیر درگاه نگه می‌داشت (۲ ثانیه) ⇒ خطر ته‌کشیدن connection pool.
بعد از فیکس: **۰٫۰۲ ثانیه**. پس فیکس درست و مفید است، ولی کامنت `main.py:1272`
که می‌گوید «ALL of them claim successfully → gateway verified N times» باید تصحیح شود.
