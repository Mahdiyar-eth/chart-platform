## بخش ۰ — قوانین کار هرمس (این را اول و کامل بخوان)

مدل مجری (DeepSeek v4 Flash) سریع و ارزان است اما پنجرهٔ استدلال کوتاه‌تری دارد.
پس این قوانین **اجباری** هستند، نه پیشنهاد:

### ۰.۱ قانون اندازهٔ تسک
- **هر بار فقط یک تسک (یک ID مثل `A3`).** هرگز دو تسک را با هم شروع نکن.
- هر تسک باید در **کمتر از ۲۵۰ خط دیف** تمام شود. اگر دیف بزرگ‌تر شد → تسک را بشکن و در گزارش بنویس «تسک X به X-a و X-b شکسته شد».
- هر تسک = **یک کامیت مستقل** با پیام `[<ID>] <خلاصهٔ فارسی یا انگلیسی>`.

### ۰.۲ قانون تست-اول (Test-First) — بدون استثنا
برای هر تسکی که رفتار سیستم را عوض می‌کند:
1. اول تست بنویس که **الان قرمز است** (اجرا کن و خروجی قرمز را در گزارش بیاور).
2. بعد کد را بنویس.
3. دوباره اجرا کن و خروجی سبز را در گزارش بیاور.
4. `bash scripts/ci.sh` را کامل اجرا کن — باید سبز باشد.

> اگر تستی ننوشتی، آن تسک **تمام نشده** است — حتی اگر کد کار کند.

### ۰.۳ خط قرمزها (هرگز دست نزن)
| مورد | چرا |
|---|---|
| `app/astrology/engine.py` (ریاضی محاسبه) | Golden Suite با دقت ۱ دقیقهٔ قوس تأیید شده |
| `app/astrology/golden_data.py` و `tests/test_golden_charts.py` | مرجع صحت موتور |
| حذف/اسکیپ کردن هر تستِ موجود برای سبز شدن CI | تقلب است؛ اگر تستی واقعاً غلط است، در گزارش دلیل بنویس و **صبر کن** |
| تغییر قیمت‌های ریالی موجود بدون تصمیم مالک | در بخش ۳ قفل شده‌اند |
| نوشتن کلید/سکرت در کد یا داکیومنت | CI اسکنر سکرت دارد و fail می‌شود |
| زبان «فال / پیش‌بینی / طالع‌بینی» در محتوا | CI اسکنر brand-language دارد |

### ۰.۴ کی وب‌سرچ کن (اجباری، نه اختیاری)
قبل از این تسک‌ها **حتماً** سرچ وب بزن و لینک منبع را در گزارش بنویس:
- **C-*** (UI/UX): الگوهای ناوبری موبایل ۲۰۲۶، bottom-nav best practice، RTL layout pitfalls، WCAG 2.2 touch target (۲۴×۲۴ حداقل / ۴۴×۴۴ توصیه‌شده).
- **D-*** (IA/منو): «mobile bottom navigation 5 items rule»، «hamburger menu vs tab bar conversion».
- **G-*** (مارکتینگ): بنچمارک نرخ تبدیل freemium، لید مگنت، ایمیل/SMS onboarding sequence.
- هر جا با یک API/کتابخانه گیر کردی (Playwright، WeasyPrint، pgvector، Zarinpal) → سرچ کن، **حدس نزن**.
- **قانون:** هر ادعای «بهترین کار این است که…» در گزارش باید یک لینک منبع داشته باشد.

### ۰.۵ کی توقف کن و بپرس (Escalation)
اگر یکی از این‌ها رخ داد، **کد ننویس**، تسک را `BLOCKED` علامت بزن و در گزارش بنویس:
- تصمیم قیمتی/محصولی که در بخش ۳ قفل نشده است.
- تسکی که نیاز به کلید/حساب بیرونی دارد (زرین‌پال واقعی، کاوه‌نگار، FCM، دامنه).
- تناقض بین این پلن و کد موجود.
- تستی که برای سبز شدن نیاز به تغییر منطق مالی دارد.

- تست‌های LLM-محور را با `ENRICH_INSIGHTS=0` بزن مگر تسک صراحتاً «تولید واقعی» بخواهد.
- برای تسک‌های تولید واقعی: **حداکثر ۱۰ فراخوانی**، مدل ارزان (`deepseek-v4-flash`)، و هزینهٔ دقیق را از `call_logs` در گزارش بیاور.
- هرگز حلقهٔ retry بی‌سقف روی LLM ننویس.

## بخش ۱ — پروژه چیست (خلاصهٔ فنی و محصولی)

**زایچه (Zayche / چارت‌نگار)** یک پلتفرم فارسی‌زبانِ خودشناسی بر پایهٔ چارت تولد است.
**پوزیشن برند:** «آینهٔ خودشناسی، نه حکم دربارهٔ آینده» — ضدِ فال، مبتنی بر شواهد.

### معماری
```
دادهٔ تولد → موتور قطعی (zoneinfo + pyswisseph) → Chart JSON کاننیکال
          → Rule Engine (Factor/Weight/Evidence) → LLM (فقط نویسنده، هرگز محاسبه‌گر)
          → QA خودکار (claim_validation + hallucination gate) → رندر (PDF/Word/داشبورد/صوت)
```

### استک
FastAPI + SQLModel + PostgreSQL 16 (+pgvector) + Redis/ARQ + pyswisseph + WeasyPrint
+ HTMX/Alpine (بدون بیلد فرانت) + Jinja2 + R2 (فایل) + زرین‌پال + بات تلگرام/بله + PWA (RTL).

### وضعیت واقعی
- **۵۶۳ تست سبز** · CI سخت‌گیر (alembic chain + prod-boot fail-closed + bandit + pip-audit + secret scan + brand-language scan).
- موتور نجومی، پرداخت، مالکیت/IDOR، ریفاند، کوپن، رفرال، CMS، ادمین — همه پیاده و تست‌شده.
- بیش از ۱۰۰ فایل مستند در `docs/` و `reports/` (چند دور ممیزی مستقل).
- **آنچه باقی مانده، «کد خراب» نیست — «مدل کسب‌وکار نیمه‌تمام + لایهٔ محصول/تجربه» است.**

### سرویس‌های فعلی
چارت رایگان · پیش‌نمایش بینش رایگان · کاوش خودشناسی (۱۰ کارت، کردیتی) · گزارش عمیق (۳ پلن ریالی) ·
چت با چارت (پلن طلایی/ماهانه) · سیناستری · بازبینی ساعت تولد · آسمان امروز/هفته · گذر کنونی · صوت گزارش · بات‌ها.

**رایگان و بدون نیاز به لاگین:**
- ساخت چارت تولد + چرخ SVG + سه‌گانهٔ اصلی
- ۳ تا ۵ بینش پیش‌نمایش (همان `api_chart_preview` موجود)

- **[جدید]** ۱ رویداد از گذرهای پیش‌رو با تحلیل کامل، به‌عنوان طعمه

**همه‌چیز دیگر = اعتبار.**

### ۳.۵ قوانین سخت اقتصاد اعتبار
1. اعتبار **هرگز منقضی نمی‌شود** (وعدهٔ فعلی در UI — نشکنش).
2. خرج اعتبار **اتمیک** است: `UPDATE ... WHERE credits >= cost RETURNING` (الگوی موجود در `explore/service.py:218`).
3. اگر تولید (LLM) شکست خورد → **اعتبار خودکار برگردد** + ردیف ledger با `reason='refund'`.
4. هر تراکنش اعتبار یک ردیف در `credit_transactions` دارد. **ثابت حسابداری:** `sum(amount) == users.credits` برای هر کاربر — این باید تست داشته باشد.
5. اعتبار **به کاربر** تعلق دارد نه به چارت. یک کاربر می‌تواند برای هر تعداد چارت خرج کند.
6. خرید اعتبار نیاز به **حساب کاربری** دارد (OTP). چارت رایگان همچنان بدون حساب.
7. سازگاری با گذشته: هر `Order` پرداخت‌شدهٔ قدیمی باید معادل استحقاقش را نگه دارد — **هیچ کاربر فعلی نباید چیزی از دست بدهد** (تسک `A6`).

## بخش ۴ — Workstream A: اقتصاد اعتبار یکپارچه 🔴 (بزرگ‌ترین کار)

**هدف:** تبدیل دو سیستم پولی موازی به **یک کیف اعتبار کاربرمحور**، بدون شکستن هیچ خریدِ گذشته.

### A1 — مدل داده و مهاجرت
**فایل‌ها:** `app/models.py`, `alembic/versions/<new>.py`

**قدم‌ها:**
1. جدول جدید `credit_prices`:
   ```
   action_key: str  (PK)      # 'report_full', 'transit_12m', ...
   title_fa: str
   credits: int
   active: bool = True
   updated_at: datetime
   ```
   → مقادیر اولیه از جدول بخش ۳.۲ سید شود (در `lifespan` مثل `PLANS_SEED`).
2. جدول جدید `entitlements`:
   ```
   id: str (uuid)
   user_id: str  (index)
   kind: str             # 'report'|'chat'|'transit'|'synastry'|'rectify'|'audio'
   chart_id: str | None  # برای استحقاق‌های وابسته به چارت
   ref_id: str | None    # report_id / forecast_id
   quantity: int = 1     # مثلاً ۲۰ پیام چت
   used: int = 0
   expires_at: datetime | None
   source: str           # 'credit'|'order'|'subscription'|'migration'
   source_ref: str | None  # credit_transaction.id یا order.id
   created_at: datetime
   ```
   ایندکس‌ها: `(user_id, kind)`, `(chart_id, kind)`.
3. `credit_transactions`: فیلد `idempotency_key: str | None` + **UNIQUE index** روی آن اضافه کن.

**تست پذیرش (`tests/test_credit_model_a1.py`):**
- migration روی DB خالی اجرا شود و `alembic check` drift ندهد.
- `credit_prices` بعد از بوت ۱۰ ردیف بخش ۳.۲ را داشته باشد.
- درج دو تراکنش با `idempotency_key` یکسان → خطای یکتایی.

**اثبات:** `venv/bin/alembic upgrade head && venv/bin/alembic check` + خروجی pytest.

### A2 — سرویس مرکزی اعتبار
**فایل جدید:** `app/credits.py`

**API دقیقی که باید بنویسی:**
```python
def get_price(session, action_key: str) -> int
    """قیمت از DB. اگر ردیف نبود → LookupError. هرگز عدد هاردکد نکن."""

def spend(session, user_id: str, action_key: str, *,
          idempotency_key: str, chart_id: str | None = None,
          meta: dict | None = None) -> CreditTransaction
    """خرج اتمیک:
       1) اگر idempotency_key قبلاً ثبت شده → همان تراکنش را برگردان (بدون خرج دوباره)
       2) UPDATE users SET credits = credits - :c WHERE id=:u AND credits >= :c RETURNING id
       3) اگر ردیفی برنگشت → InsufficientCredits (کد خطا: ZAY-CRD-001)
       4) ردیف ledger با amount منفی
    """

def refund(session, tx_id: str, reason: str) -> CreditTransaction
    """بازگشت اعتبار برای تولید شکست‌خورده. idempotent: دو بار صدا زدن = یک بار برگشت."""

def grant(session, user_id: str, amount: int, reason: str, *,
          idempotency_key: str, source_ref: str | None = None) -> CreditTransaction

def balance(session, user_id: str) -> int
```

**قوانین:**
- هیچ‌جای دیگر کد اجازه ندارد مستقیم `UPDATE users SET credits` بزند.
  بعد از این تسک: `grep -rn "SET credits" app/ | grep -v app/credits.py` باید **خالی** باشد.
- `app/explore/service.py` باید به این سرویس منتقل شود (رفتار فعلی حفظ شود: اولین کاوش رایگان).

**تست پذیرش (`tests/test_credits_service_a2.py`) — حداقل ۱۲ تست:**
1. خرج موفق → موجودی کم شد + ردیف ledger ساخته شد
2. خرج با موجودی صفر → `InsufficientCredits` و موجودی دست‌نخورده
3. خرج با موجودی دقیقاً برابر هزینه → موفق، موجودی صفر
4. idempotency: دو بار `spend` با یک کلید → یک بار خرج
5. refund idempotent
6. **ثابت حسابداری:** بعد از ۵۰ عملیات تصادفی، `sum(ledger.amount) == users.credits`
7. **رقابت هم‌زمانی:** دو `spend` موازی با موجودی ۱ → دقیقاً یکی موفق (تست با دو session)
8. `get_price` روی کلید ناموجود → LookupError
9. `grant` idempotent
10. قیمت از DB خوانده می‌شود نه ثابت کد (قیمت را در DB عوض کن، `spend` مبلغ جدید را خرج کند)

**مشخصات دقیق الگوریتم:**

- **خروجی هر رویداد:**

**لایهٔ ۶ — تست موبایل واقعی:** چک‌لیست تصویری برای اجرا روی گوشی مالک (این را هرمس نمی‌تواند خودش انجام دهد — فقط چک‌لیست را آماده کن).

**خروجی نهایی:** `docs/qa/FULL-TEST-REPORT-<date>.md` با جدول: `سناریو · لایه · نتیجه · مدرک (لاگ/اسکرین‌شات) · باگ‌های یافته‌شده`

### E4 — قانون «هیچ باگی بدون تست بسته نمی‌شود»
برای هر باگی که پیدا کردی:
1. اول تستی بنویس که باگ را بازتولید کند (قرمز)
2. فیکس کن
3. سبز شدن را نشان بده
4. در گزارش: `باگ · فایل:خط · علت ریشه‌ای · فیکس · تست`

## بخش ۱۰ — Workstream G: مارکتینگ، برند و جذب کاربر 🟠

**تشخیص:** محصول ساخته شده، اما **موتور رشد ساخته نشده**. آنالیتیکس نصب است ولی صفر رویداد ثبت می‌کند (F10)،
هیچ مسیر جمع‌آوری لید نیست، و قیف بعد از «چارت رایگان» رها می‌شود.
**بدون این بخش، همهٔ کارهای دیگر کاربر نخواهند داشت.**

### G1 — ابزار سنجش قیف (اول این — بدون داده، بقیه حدس است)
**فایل‌ها:** `app/templates/base.html`, `app/static/js/track.js` (جدید)

Umami رویداد سفارشی پشتیبانی می‌کند. **این رویدادهای دقیق را پیاده کن** (نام‌ها را عوض نکن):

**داشبورد قیف** در پنل ادمین: نرخ تبدیل هر گام + جدول ریزش.

**تست پذیرش:** ۵ تست Playwright که وجود فراخوانی رویداد را در نقاط کلیدی اثبات کند.

### G2 — بهینه‌سازی قیف (بعد از G1)
**قیف هدف:**
```
بازدید → چارت رایگان (بدون اصطکاک) → بینش رایگان → «آها!» لحظهٔ ارزش
→ ثبت‌نام (برای نگه‌داشتن چارت) → ۱ کاوش رایگان → پیشنهاد اعتبار → خرید
→ گزارش/گذر → اعلان هفتگی → بازگشت → خرید بعدی
```
**نقاط اصطکاکی که باید فیکس شوند:**
1. **لحظهٔ ارزش خیلی دیر می‌آید:** کاربر بعد از چارت، فقط نمودار می‌بیند. باید **بلافاصله** ۳ بینش شخصی و تیز ببیند.
2. **دلیلی برای ثبت‌نام وجود ندارد:** «چارتت را ذخیره کن + ۱ کاوش رایگان بگیر» را صریح نشان بده.
3. **پیشنهاد خرید در لحظهٔ اشتباه:** پیشنهاد باید بعد از مصرف کاوش رایگان بیاید، نه قبلش.
4. **بن‌بست بعد از خرید:** بعد از دریافت گزارش، هیچ «قدم بعدی» پیشنهاد نمی‌شود → گذرهای پیش‌رو را پیشنهاد بده.
5. **قیمت بدون لنگر:** همیشه پک بزرگ‌تر را کنار پک انتخابی نشان بده («۲۰٪ ارزان‌تر»).

### G3 — لید مگنت و جمع‌آوری مخاطب

  → آن را پشت «شمارهٔ موبایل یا ایمیل» قرار بده (کم‌اصطکاک: فقط یک فیلد).
- خبرنامهٔ «آسمان هفته»: هفتگی، تأملی، با یک بینش عمومی + یک CTA شخصی.
- مدل داده: `subscribers(contact, channel, source, consent_at, unsubscribed_at)` — **رضایت صریح** و لینک لغو اشتراک اجباری (بخش حریم خصوصی موجود را رعایت کن).

3. اگر تسکی را نصفه رها کردی، `PARTIAL` بزن و **دقیقاً** بنویس چه مانده.
4. اگر پلن جایی با واقعیت کد نخواند، آن را در بخش ۵ بنویس — این باارزش‌ترین بخش گزارش برای دور بعد است.
