# بعد: عملکرد و هزینه

پاسخ مدل: go/deepseek-v4-pro

## تحلیل عملکرد و هزینه — چارت تولد

> این تحلیل بر پایه‌ی `OVERVIEW` و کد ارائه‌شده‌ی `app/main.py` است. برای برخی موارد که جزئیات کد در دسترس نیست، صراحتاً «نامشخص» نوشته شده است.

### اولویت‌بندی کلی مسائل عملکردی/هزینه‌ای

| # | اولویت | موضوع | مدرک | اثر |
|---|--------|-------|-------|-----|
| ۱ | **P0** | عدم بررسی نتیجه‌ی `_enqueue_report` در callback پرداخت | `app/main.py` → `api_payment_verify` | سفارش «paid» ثبت می‌شود ولی گزارش هرگز تولید نمی‌شود؛ ریسک ریفاند و پشتیبانی بالا |
| ۲ | **P1** | ایجاد Redis pool جدید در هر بار enqueue | `app/main.py` → `_enqueue_report` | تأخیر در ثبت گزارش + مصرف اتصال‌های Redis |
| ۳ | **P1** | تولید فایل صوتی سنکرون در مسیر API | `app/main.py` → `api_report_audio` | مسدود شدن thread سرور، تولید تکراری، و پر شدن `/tmp` |

| ۵ | **P1** | هزینه LLM در حالت fallback و QA retry مانیتور نشده است | `app/core/llm.py`، `app/report/worker.py`، `qa.py` (طبق OVERVIEW) | اگر سهمیه‌ی pro تمام شود، fallback به سرویس‌های پرداخت‌به‌ازای توکن ممکن است هزینه را از حالت ثابت خارج کند |

| ۷ | **P2** | دوبار فراخوانی `get_current_user` در یک تابع | `_compute_and_save_chart` در `app/main.py` | دو بار کار با سشن/DB اضافی |

### ۱) سرعت رندر و درخواست‌های HTTP

#### ۱.۱. `_enqueue_report` — ساخت Redis pool در هر تماس (P1)
```python
async def _push():
    redis = await create_pool(RedisSettings.from_dsn("redis://127.0.0.1:6379/0"))
    ...
    await redis.aclose()
asyncio.run(_push())
```
این الگو برای هر بار ثبت گزارش یک connection pool جدید می‌سازد و می‌بندد. در حجم معمولی شاید قابل قبول باشد، ولی در موج سفارش‌ها (همان‌طور که در `api_payment_verify` هم صدا زده می‌شود) باعث:
- افزایش latency هر درخواستِ ساخت گزارش
- مصرف فایل‌دسکریپتور و اتصال‌های Redis
- بلاک شدن event loop اصلی FastAPI (چون `asyncio.run` در مسیر sync اجرا می‌شود و threadpool را اشغال می‌کند)

**پیشنهاد:** از یک ARQ pool سراسری یا یک کلاینت Redis آماده در `lifespan` استفاده شود؛ یا `_enqueue_report` از طریق `asyncio` در یک مسیر async اجرا شود.

#### ۱.۲. `api_report_audio` — تولید صدا در همان درخواست (P1)
```python
@app.get("/api/reports/{report_id}/audio")
def api_report_audio(...):
    ...
    if not out.exists():
        ...
        asyncio.run(_gen())   # edge_tts خارجی
    return FileResponse(...)
```
مسائل:
- هر درخواست دانلود صدا که فایل آن وجود نداشته باشد، یک فراخوانی شبکه خارجی (`edge_tts`) انجام می‌دهد و thread سرور را برای چند ثانیه/ده‌ها ثانیه مشغول می‌کند.
- هیچ قفل و هماهنگی بین درخواست‌های هم‌زمان وجود ندارد؛ چند کاربر ممکن است هم‌زمان همان فایل را تولید کنند.
- فایل در `/tmp` ذخیره می‌شود و هیچ پاکسازی خودکار ندارد؛ با چند ده گزارش، دیسک پر می‌شود.

**پیشنهاد:** تولید MP3 به صف ARQ منتقل شود، فایل در R2 ذخیره شود و لینک presigned با TTL کوتاه برگردد؛ یا حداقل از یک lock (Redis/file) و پاکسازی دوره‌ای استفاده شود.

#### ۱.۳. نبود ایندکس‌های مهم (P1)
در کد `main.py` این الگوها زیاد تکرار شده‌اند:
```python
select(Order).where(Order.chart_id == chart_id, Order.status == "paid").first()
select(Report).where(Report.chart_id == chart_id).order_by(Report.created_at.desc()).first()
```
با رشد جدول‌ها، این کوئری‌ها بدون ایندکس مرکب به سرعت کند می‌شوند.

**ایندکس‌های پیشنهادی:**
- `Order(chart_id, status)`
- `Order(plan_key, status, chart_id, secondary_chart_id)` برای مسیر سیناستری
- `Report(chart_id, created_at)`
- `BirthProfile(user_id)`

این مورد کاملاً در حوزه‌ی عملکرد DB است و باید پیش از رشد کاربران جدی گرفته شود.

#### ۱.۴. کوئری‌های تکراری در `_compute_and_save_chart` (P2)
```python
user_id=user_id or (get_current_user(request).id if get_current_user(request) else None)
```
`get_current_user(request)` دو بار فراخوانی می‌شود. بسته به پیاده‌سازی آن در `app/auth.py`، این می‌تواند دو بار decode کوکی یا دو بار query به DB باشد.

**پیشنهاد:** یک بار فراخوانی شود:
```python
current_user = get_current_user(request)
user_id=user_id or (current_user.id if current_user else None)
```

#### ۱.۵. نبود کش برای خروجی‌های قطعی (P2)
- `chart_page` هر بار `big_three` و `render_chart_svg` و ویجت‌های SVG را محاسبه می‌کند. داده‌ی چارت تغییرناپذیر است؛ می‌توان SVG و big_three را با کلید `chart_id` در Redis/حافظه کش کرد.
- `api_chart_transits` و `transit_page` هر بار `compute_transits` را صدا می‌زنند. ترانزیت روزانه است؛ می‌توان تا ۱ ساعت یا تا نیمه‌شب کش کرد.
- `api_plans` هر بار DB را می‌خواند؛ پلن‌ها به ندرت تغییر می‌کنند؛ می‌توان با TTL و invalidation کش کرد.
- `api_report_docx` هر بار فایل Word را از نو می‌سازد؛ می‌توان فایل تولیدشده را در R2/فایل سیستم کش کرد.

### ۲) هزینه‌ی LLM

#### ۲.۱. وضعیت فعلی
- اشتراک ثابت `$10/ماه` برای DeepSeek V4 Pro از طریق opencode.ai (طبق OVERVIEW).
- سهمیه‌ی pro: ۳۴۵۰ درخواست در هر ۵ ساعت.
- فلش: ۱۲۶٬۶۰۰ درخواست در هر ۵ ساعت.

#### ۲.۲. تخمین ظرفیت تولید گزارش
با فرض هر گزارش کامل ۱۳–۱۴ بخش (یک درخواست LLM برای هر بخش):

```
درخواست‌های روزانه پرو = 3450 × (24 / 5) ≈ 16,560
گزارش‌های روزانه با 13 بخش ≈ 16,560 / 13 ≈ 1,274 گزارش
گزارش‌های روزانه با 14 بخش ≈ 16,560 / 14 ≈ 1,182 گزارش
```
این ظرفیت بسیار خوب است، **اما**:
- اگر QA خودکار (در `app/report/qa.py`) یک بخش را رد کند و worker دوباره تولید کند (`retry=2`)، مصرف LLM تا ۲ برابر افزایش می‌یابد.
- اگر درخواست‌های چت (`v4-flash`) و ترانزیت‌های هفتگی و فری‌میم‌ها هم به همین سهمیه فشار بیاورند، ممکن است سهمیه زودتر تمام شود.

#### ۲.۳. ریسک fallback به سرویس‌های متغیر
ROUTER در `app/core/llm.py` به ترتیب از `go → gemini فری → avalai → deepseek رسمی` استفاده می‌کند.
- Gemini فری با ۲۴ کلید، اما محدودیت‌های خاص خود را دارد.
- AvalAI و DeepSeek رسمی احتمالاً پرداخت‌به‌ازای توکن دارند.
- اگر سهمیه‌ی go تمام شود یا خطا بدهد، سرویس به fallback می‌رود و **هزینه گزارش از حالت اشتراک ثابت خارج می‌شود**.

**نکته‌ی مبهم:** قیمت دقیق به‌ازای توکن در AvalAI یا DeepSeek رسمی در سند نیامده است؛ صرفاً باید به‌عنوان «نامشخص» علامت بزنیم و حتماً مانیتور شود.

#### ۲.۴. حجم توکن هر بخش
- طبق OVERVIEW، عمق هر بخش ۷۰۰–۱۱۰۰ کلمه‌ی فارسی است.
- خروجی با `max_tokens=8192` محدود شده، اما توکن‌های فارسی معمولاً گران‌تر از انگلیسی هستند (یک کلمه‌ی فارسی ممکن است ۱.۵ تا ۲.۵ توکن مصرف کند).
- اگر هر بخش به طور میانگین ۱۲۰۰–۱۸۰۰ توکن خروجی و ورودی هم حدود ۱۵۰۰–۲۵۰۰ توکن داشته باشد، هر گزارش حدود ۲۵هزار تا ۴۰هزار توکن مصرف می‌کند.
- در حالت اشتراک ثابت این مشکلی نیست، ولی در fallback ممکن است هزینه‌ی قابل توجهی بسازد.

**پیشنهاد:**
- از جدول `LLMRun` (که در `models.py` import شده) برای ثبت دقیق توکن، مدل، latency و هزینه استفاده شود و داشبورد/هشدار بودجه داشته باشید.
- نرخ شکست QA و بازتولیدها را مانیتور کنید؛ اگر >۱۵٪ باشد، باید پرامپت‌ها اصلاح شوند.

### ۳) حجم خروجی و فضای ذخیره‌سازی

#### ۳.۱. PDF
- طبق تست E2E، گزارش گلد با ۱۴ بخش `PDF 261KB` است. این حجم بسیار مناسب است و مشکلی ایجاد نمی‌کند.
- PDF در R2 ذخیره می‌شود و با presigned URL کوتاه‌مدت دانلود می‌شود. هزینه‌ی R2 معمولاً مقرون‌به‌صرفه است.

#### ۳.۲. فایل صوتی (MP3)
- در `api_report_audio` فایل صوتی مستقیماً در `/tmp` ساخته می‌شود.
- هیچ پاکسازی خودکار یا TTL ندارد.
- حجم یک MP3 برای متن ۱۳ بخش ممکن است بین **۲ تا ۶ مگابایت** باشد.
- با چند صد کاربر، دیسک سرور به سرعت پر می‌شود و حتی ممکن است سرویس از کار بیفتد.

#### ۳.۳. فایل Word (DOCX)
- در `api_report_docx` به صورت on-the-fly ساخته می‌شود.
- حجم آن احتمالاً بین ۱۰۰ تا ۳۰۰ کیلوبایت است.
- چون هر بار ساخته می‌شود، CPU اندکی مصرف می‌کند. می‌توان فایل تولیدشده را در R2 ذخیره و لینک presigned برگشت تا درخواست‌های بعدی سبک‌تر شوند.

#### ۳.۴. تصاویر SVG و کارت اشتراک
- SVGها حجم بسیار کمی دارند.
- `api_share_card` طبق توضیح کد، «rendered + cached on first request» است، اما جزئیات کش در کد دیده نمی‌شود. اگر cache file-based باشد، باید مطمئن شوید که مسیر ذخیره‌سازی خارج از دایرکتوری‌های عمومی نیست و پاکسازی دارد؛ در غیر این صورت با انباشت فایل‌های PNG با ابعاد ۱۲۰۰×۶۳۰ ممکن است فضای ذخیره‌سازی زیاد شود.

### ۴) کش (Caching)

| لایه | وضعیت فعلی | اقدام پیشنهادی |
|------|------------|----------------|
| چارت SVG / big_three | بدون کش، در هر بار رندر صفحه دوباره محاسبه می‌شود | کش در Redis/حافظه با کلید `chart:svg:{chart_id}` |
| ترانزیت روزانه | بدون کش، در `api_chart_transits` و `transit_page` هر بار محاسبه می‌شود | کش با TTL یک‌ساعته یا تا نیمه‌شب |
| پلن‌ها | کوئری مستقیم DB در `api_plans` و `plans_page` | کش در حافظه/Redis با invalidation ادمین |
| DOCX | ساخته‌شده در هر دانلود | ذخیره در R2/فایل و ارائه با presigned URL |
| فایل صوتی | `/tmp` بدون TTL | انتقال به R2 و لینک presigned |
| پیش‌نمایش رایگان | rule-based بدون LLM، ولی هر بار اجرا می‌شود | می‌توان با کلید chart_id کش کرد |
| Landing page | بدون مشکل عمده | می‌توان از CDN یا Cache-Control برای static استفاده کرد |

**نکته:** CSP فعلی `unsafe-inline/eval` برای Alpine مستند شده است، اما روی سرعت رندر تأثیر چندانی ندارد.

### ۵) دیتابیس و اتصال

- SQLModel با SQLAlchemy و `engine` سراسری استفاده شده است. Pooling به صورت پیش‌فرض فعال است.
- `get_session` به درستی session را مدیریت می‌کند.
- کوئری‌های پرتکرار بدون ایندکس ممکن است در مقیاس واقعی مشکل‌ساز شوند (همان P1 بالا).
- `api_admin_prompts_list` تمام `PromptVersion`ها را با `order_by version.desc()` می‌خواند و سپس با `seen` موارد تکراری را رد می‌کند. با رشد تاریخچه‌ی پرامپت‌ها، این کوئری سنگین می‌شود. پیشنهاد: از `DISTINCT ON` یا `LIMIT 1` به ازای هر کلید استفاده شود.

### ۶) نکات نامشخص

- **Worker concurrency تنظیمات ARQ:** در OVERVIEW اشاره شده `chart-worker` با ARQ اجرا می‌شود، اما تعداد worker ها یا `max_jobs` مشخص نیست. ظرفیت واقعی تولید گزارش به این عدد بستگی دارد.
- **هزینه‌ی دقیق fallback:** AvalAI و DeepSeek رسمی قیمت مشخصی در سند ندارند؛ برای تحلیل هزینه نیاز به مانیتورینگ دقیق است.
- **پیاده‌سازی `render_share_card`:** فقط توضیح داده شده که cached است؛ مکانیزم کش و محل ذخیره‌سازی نامشخص است.
- **رفتار `chat_answer`:** مشخص نیست سنکرون یا async است. اگر سنکرون باشد و LLM latency بالا داشته باشد، ممکن است threadpool را اشغال کند.

### جمع‌بندی این بُعد

عملکرد فعلی برای مقیاس کوچک و متوسط قابل قبول است، اما چند ریسک واضح وجود دارد:
- **بحرانی‌ترین مشکل** نادیده گرفتن نتیجه‌ی `enqueue` در `api_payment_verify` است که مستقیماً به تجربه‌ی کاربر و ریفاند می‌انجامد.
- **در مقیاس رشد** نبود ایندکس‌ها و ساخت Redis pool در هر درخواست می‌تواند DB و شبکه را به‌شدت کند کند.
- **هزینه‌ی LLM** تا وقتی در اشتراک ثابت `$10` بماند عالی است؛ ولی وابستگی به سهمیه و fallback متغیر باید مانیتور شود.
- **حجم خروجی** PDF عالی است؛ فایل صوتی `/tmp` بدون مدیریت، ریسک عملیاتی جدی دارد.
- با افزودن کش در لایه‌ی قطعی (چارت، ترانزیت، پلن‌ها) و اصلاح الگوهای Redis، می‌توان مصرف CPU و latency را بدون افزایش هزینه‌ی سخت‌افزاری کاهش داد.
