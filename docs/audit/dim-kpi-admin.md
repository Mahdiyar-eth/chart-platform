# بعد: KPI داشبورد و ادمین

پاسخ مدل: go/deepseek-v4-pro

## تحلیل پنل ادمین و KPI

### ۱) وضعیت فعلی متریک‌های موجود

بر اساس کد ارائه‌شده (`app/main.py`) و سند `OVERVIEW`، **هیچ داشبورد KPI یا API تجمیع آمار وجود ندارد**. تنها endpointهای ادمین موجود، عملیات مدیریتی محدود زیر هستند:

- `POST /api/admin/coupons` (تابع `admin_coupon_create`) — ایجاد کوپن تخفیف  
- `GET /api/admin/coupons` (تابع `admin_coupons`) — فهرست کوپن‌ها  
- `GET /api/admin/prompts` (تابع `admin_prompts_list`) — مشاهده‌ی override های پرامپت  
- `POST /api/admin/prompts/{prompt_key}` (تابع `admin_prompt_save`) — ذخیره‌ی پرامپت جدید  
- `POST /api/admin/orders/{order_id}/refund` (تابع `admin_refund`) — ریفاند سفارش پرداخت‌شده و برگرداندن استفاده کوپن  
- `POST /api/admin/orders/{order_id}/regenerate` (تابع `admin_regenerate`) — صف‌بندی مجدد تولید گزارش ناموفق  

در هیچ‌یک از این Routeها خروجی آماری (درآمد، تعداد گزارش، مصرف LLM و…) محاسبه یا نمایش داده نمی‌شود.  
در `OVERVIEW` (بخش ۶ و ۷) به وجود `audit log` و هزینه‌ی ثابت LLM با سهمیه‌ی درخواست اشاره شده، اما هیچ Route برای **خواندن** audit log یا **مشاهده‌ی مصرف سهمیه** وجود ندارد.

داده‌های خام مورد نیاز برای KPI در مدل‌های دیتابیس (`app/models.py`) موجودند:  
- `Order` (شامل `status`، `amount_rial`، `plan_key`، `coupon_id`، `paid_at`)  
- `Report` (شامل `status`، `metrics`، `created_at`)  
- `LLMRun` (اطلاعات اجرای LLM: provider، مدل، تعداد توکن، خطا و …)  
- `User` (کاربران ثبت‌نام‌شده)  
- `Subscription` (اشتراک‌ها با تاریخ فعال‌سازی و انقضا)  

اما هیچ‌کدام از این داده‌ها تجمیع یا به‌صورت API در اختیار ادمین قرار نمی‌گیرد.

### ۲) قابلیت‌های عملیاتی ادمین موجود و کاستی‌ها

**موجود:**  
- مدیریت کوپن (ایجاد و فهرست)  
- مدیریت پرامپت‌ها (نسخه‌بندی و فعال‌سازی)  
- ریفاند سفارش  
- بازتولید گزارش  

**کاستی‌های عملیاتی مهم (بدون داشبورد):**  
- **جستجو/فیلتر/لیست سفارشات** وجود ندارد؛ فقط ریفاند برای یک order_id مشخص.  
- **مدیریت کاربران** (مشاهده، مسدودسازی، تغییر نقش) وجود ندارد.  
- **مدیریت اشتراک‌ها** (تمدید دستی، لغو) وجود ندارد.  
- **مدیریت پلن‌ها** (ویرایش قیمت، فعال/غیرفعال‌سازی) وجود ندارد؛ پلن‌ها فقط در `lifespan` بذرپاشی می‌شوند.  
- **مشاهده‌ی audit log** وجود ندارد (فقط نوشتن انجام می‌شود).  
- **مشاهده‌ی وضعیت صف/Worker** وجود ندارد؛ اگر Worker خراب شود یا صف پر شود، ادمین از طریق UI مطلع نمی‌شود.

### ۳) KPIهای حیاتی غایب و اولویت‌بندی

#### 🚨 P0 (بحرانی — بدون این‌ها عملیات کور است)

1. **درآمد خالص و کل**  
   - مجموع `Order.amount_rial` برای `status='paid'` منهای `refunded` در بازه‌ی دلخواه.  
   - تفکیک به پلن (`plan_key`) و روز/ماه.  
   - **چرا:** پایه‌ی هر تصمیم مالی و ارزیابی سلامت کسب‌وکار.

2. **نرخ تبدیل قیف فروش**  
   - تعداد `Chart` ایجاد شده → تعداد `Order` ایجاد شده → تعداد `paid`.  
   - داده‌های هر سه مرحله در جداول موجود است، اما تجمیع نشده.

3. **سلامت تولید گزارش**  
   - تعداد گزارش‌های `queued`, `running`, `done`, `failed` (از جدول `Report`).  
   - نرخ موفقیت (٪ done)، میانگین زمان از شروع تا پایان، خطاهای اخیر.  
   - **چرا:** اگر Worker یا LLM از کار بیفتد، درآمد متوقف می‌شود؛ watchdog فعلی فقط 500 HTTP را می‌بیند.

4. **مصرف و سهمیه‌ی LLM**  
   - تعداد درخواست‌های موفق/ناموفق به تفکیک provider (از `LLMRun`)، تخمین مصرف سهمیه‌ی pro (3450 درخواست / 5 ساعت) و flash.  
   - **چرا:** هزینه‌ی اشتراک ثابت است، اما اتمام سهمیه یعنی توقف کامل تولید گزارش. باید مانیتور و آلارم داشته باشد.

#### ⚠️ P1 (مهم — برای تصمیم‌گیری‌های میان‌مدت)

5. **کاربران و نرخ تبدیل به مشتری**  
   - تعداد کاربران ثبت‌شده (`User`)، تعداد خریداران یکتا، نرخ تبدیل ثبت‌نام → خرید.  
   - کاربران فعال بر اساس کوکی ورود / `last_login` (اگر فیلد موجود باشد).

6. **اشتراک‌ها**  
   - تعداد اشتراک فعال، درآمد ماهانه‌ی اشتراک، نرخ تمدید (در صورت ردیابی).  
   - در کد `activate_subscription` صدا زده می‌شود اما هیچ نمایشی برای ادمین وجود ندارد.

7. **میانگین زمان تولید گزارش**  
   - اختلاف `created_at` (زمان queued) تا `updated_at` (زمان done/failed) در `Report`.  
   - به شناسایی گلوگاه‌ها (LLM کند، صف طولانی) کمک می‌کند.

8. **کیفیت گزارش و QA**  
   - نرخ رد QA، تعداد retryها، میانگین امتیاز کیفیت (اگر در `metrics` ذخیره شود).  
   - در `OVERVIEW` به `qa.py` و `Report.metrics` اشاره شده، اما هیچ تجمیعی وجود ندارد.

9. **Audit Log خواندنی**  
   - مشاهده‌ی رخدادهای ادمین (چه کسی چه کرد).  
   - هم‌اکنون فقط نوشتن انجام می‌شود (`app.security.audit`) — خواندن وجود ندارد.

#### 🔧 P2 (بهبود — برای بهینه‌سازی و رشد)

10. **درآمد به تفکیک پلن و کوپن**  
    - تحلیل اثربخشی تخفیف‌ها (مثلاً WELCOME10) و سهم هر پلن از درآمد.

11. **نرخ ریفاند**  
    - نسبت سفارشات `refunded` به `paid` — شاخص رضایت و کیفیت محصول.

12. **مصرف قابلیت‌های ویژه**  
    - تعداد استفاده از synastry, rectify, chat, transit pages.

13. **مانیتورینگ فنی**  
    - طول صف Redis، وضعیت Worker (heartbeat)، مصرف CPU/حافظه، خطاهای 500 در بازه.

### ۴) جمع‌بندی این بُعد

پنل ادمین فعلی **تنها قادر به انجام چند عملیات مدیریتی محدود** (کوپن، پرامپت، ریفاند، بازتولید) است و **هیچ‌گونه داشبورد KPI یا آمار تجمیعی ارائه نمی‌دهد**. داده‌های لازم برای درآمد، گزارش‌ها، کاربران، اشتراک‌ها و مصرف LLM در مدل‌های دیتابیس موجودند، اما هیچ لایه‌ای برای استخراج و نمایش آن‌ها ساخته نشده است.  
این وضعیت، تصمیم‌گیری‌های عملیاتی (مثل «آیا کمپین تخفیف مؤثر بوده؟»، «آیا Worker سالم است؟»، «چقدر تا اتمام سهمیه LLM فاصله داریم؟») را غیرممکن می‌کند و در شرایط بروز خطا، تیم را تا رسیدن مشتری ناراضی، ناآگاه نگه می‌دارد.

اولویت فوری: ساخت یک `GET /api/admin/dashboard` یا صفحه‌ی `/admin` با حداقل KPIهای P0 (درآمد، نرخ تبدیل، سلامت گزارش، مصرف LLM). سپس در گام بعد، KPIهای P1 و ابزارهای عملیاتی تکمیلی (لیست سفارشات، مدیریت کاربران و اشتراک‌ها) اضافه شوند. این کار با استفاده از داده‌های موجود در PostgreSQL قابل انجام است و نیازی به تغییر در زیرساخت اصلی ندارد.
